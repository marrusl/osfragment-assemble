# osfragment-assemble

A tool for composing bootc-compatible OS image builds from fragment OCI images.

New to the project? Start with [the design explainer](docs/design.md): what a fragment is, why fragments are standard OCI images, and what the tool deliberately leaves to dnf, your configuration tooling, and your builder. Short on time? [The design overview](docs/design-overview.md) makes the same argument at half the length. Prefer to look at real files? [The nvidia-driver-run fragment](examples/fragments/nvidia-driver-run/README.md) is a complete, working one explained file by file.

## What it does

osfragment-assemble reads a YAML manifest declaring a base bootc-compatible image and a set of fragment OCI images, then generates a Containerfile. It can also generate a MachineOSConfig YAML for OpenShift/OKD on-cluster layering. Fragments are standard OCI images that package repo configs, RPM GPG keys, config files, systemd presets, and hooks into reusable units. The tool handles ordering (repo files before packages, packages before config files, config files before hooks), deduplication (identical repo definitions from multiple fragments), and optionally pins all references to content-addressed digests.

## Getting Started

### Prerequisites

- skopeo (authenticated to any private registries your fragments use)

### Install

**Homebrew (macOS, Apple Silicon):**

```bash
brew tap marrusl/osfragment-assemble
brew install osfragment-assemble
```

**Fedora / CentOS Stream / RHEL (via COPR):**

```bash
dnf copr enable mrussell/osfragment-assemble
dnf install osfragment-assemble
```

**Pre-built binaries:**

Available from [GitHub Releases](https://github.com/marrusl/osfragment-assemble/releases) for Linux (x86_64, arm64) and macOS (arm64).

### Build from source

Requires a Rust toolchain (1.70 or later).

```bash
cargo build --release
```

The binary will be at `target/release/osfragment-assemble`.

### Inspect a fragment

Examine a published fragment's metadata and contents:

```bash
osfragment-assemble inspect quay.io/marrusl2/fragments/tailscale:1.82.0
```

### Generate a Containerfile

Pre-built fragment images are available at `quay.io/marrusl2/fragments/`. Generate a Containerfile using them:

```bash
osfragment-assemble --manifest examples/manifests/full.yaml --output Containerfile
```

The manifest at `examples/manifests/full.yaml` already points to these public images, so no editing is needed. Review the generated Containerfile and make any changes you need before building.

### Build the final image

Requires podman (or another OCI builder).

```bash
podman build -f Containerfile -t my-bootc-image:latest .
```

## Example

Given this manifest with an EPEL repo fragment and a CIS hardening fragment:

```yaml
apiVersion: osfragment/v1alpha1
kind: Composition

base: quay.io/centos-bootc/centos-bootc:stream10

fragments:
  - image: quay.io/marrusl2/fragments/epel:10
    packages: [htop, tmux]
  - image: quay.io/marrusl2/fragments/cis-hardening:2.1
```

osfragment-assemble generates:

```dockerfile
# Generated by osfragment-assemble v0.1.0
# Manifest: osfragment-assemble.yaml
# Fragments: epel, cis-hardening
# Override summary: no file path collisions detected

# --- Base ---
FROM quay.io/centos-bootc/centos-bootc:stream10

# --- Repo files ---
COPY --from=quay.io/marrusl2/fragments/epel:10 /fragment/tree/etc/yum.repos.d/ /etc/yum.repos.d/
COPY --from=quay.io/marrusl2/fragments/epel:10 /fragment/tree/etc/pki/rpm-gpg/ /etc/pki/rpm-gpg/

# --- Packages ---
RUN dnf install -y \
        htop \
        tmux \
    && dnf clean all \
    && rm -rf /var/cache/dnf /var/log/dnf* /var/log/hawkey.log /var/lib/dnf/history.sqlite* \
    && rm -rf /run/rhsm /run/selinux-policy /var/log/rhsm /var/lib/rhsm /var/cache/ldconfig/aux-cache

# --- Config files ---
COPY --from=quay.io/marrusl2/fragments/cis-hardening:2.1 /fragment/tree/ /

# --- Hooks ---
RUN --mount=type=bind,from=quay.io/marrusl2/fragments/cis-hardening:2.1,source=/fragment/hook,target=/frag-hook,z \
    /frag-hook/entrypoint

# Apply systemd presets from fragments
RUN systemctl preset-all --preset-mode=enable-only 2>/dev/null || true

# --- Phase: validation (90) ---
RUN bootc container lint
```

Repo files land before packages, config files land after packages (so they aren't overwritten by RPM defaults), and hooks run last. Hooks are bind-mounted rather than copied, so the hook files themselves never become part of the image.

### Example: an entitlement (build-mount) fragment

Given this manifest pairing a digest-pinned entitlement fragment (carrying an encumbered package) with the cis-hardening fragment, which runs a build hook:

```yaml
base: registry.redhat.io/rhel10/rhel-bootc:latest
fragments:
  - image: quay.io/your-username/rhel-entitlement@sha256:<digest>
    packages: [rhel-system-roles]
  - image: quay.io/marrusl2/fragments/cis-hardening:2.1
```

osfragment-assemble generates:

```dockerfile
# Generated by osfragment-assemble v0.1.0
# Manifest: osfragment-assemble.yaml
# Fragments: rhel-entitlement, cis-hardening
# Override summary: no file path collisions detected

# --- Base ---
FROM registry.redhat.io/rhel10/rhel-bootc:latest

# --- Packages ---
# Build mounts below supply credential material the build host may not
# have. A subscribed RHEL host already injects its own entitlement into
# every build step, so an entitlement fragment is redundant there and can
# be omitted. Other credential mounts, such as mirror client certs or
# proxy CA bundles, are still required regardless of host.
RUN --mount=type=bind,from=quay.io/your-username/rhel-entitlement@sha256:<digest>,source=/fragment/mount/run/secrets/etc-pki-entitlement,target=/run/secrets/etc-pki-entitlement,ro,z \
    --mount=type=bind,from=quay.io/your-username/rhel-entitlement@sha256:<digest>,source=/fragment/mount/run/secrets/rhsm,target=/run/secrets/rhsm,ro,z \
    dnf install -y \
        rhel-system-roles \
    && dnf clean all \
    && rm -rf /var/cache/dnf /var/log/dnf* /var/log/hawkey.log /var/lib/dnf/history.sqlite* \
    && rm -rf /run/rhsm /run/selinux-policy /var/log/rhsm /var/lib/rhsm /var/cache/ldconfig/aux-cache

# --- Config files ---
COPY --from=quay.io/marrusl2/fragments/cis-hardening:2.1 /fragment/tree/ /

# --- Hooks ---
RUN --mount=type=bind,from=quay.io/your-username/rhel-entitlement@sha256:<digest>,source=/fragment/mount/run/secrets/etc-pki-entitlement,target=/run/secrets/etc-pki-entitlement,ro,z \
    --mount=type=bind,from=quay.io/your-username/rhel-entitlement@sha256:<digest>,source=/fragment/mount/run/secrets/rhsm,target=/run/secrets/rhsm,ro,z \
    --mount=type=bind,from=quay.io/marrusl2/fragments/cis-hardening:2.1,source=/fragment/hook,target=/frag-hook,z \
    /frag-hook/entrypoint

# Apply systemd presets from fragments
RUN systemctl preset-all --preset-mode=enable-only 2>/dev/null || true

# --- Phase: validation (90) ---
RUN bootc container lint
```

Notice the hook RUN: it mounts cis-hardening's `hook/` as the code to run, and separately mounts the entitlement fragment's credentials, so a hook that shells out to dnf authenticates just as the package step does.

Mount fragments must be digest-pinned, via `@sha256:` in the manifest or `--pin-digests` at generate time. The credential rides both the package step and every hook step, and the tool itself commits none of it, but hook code runs as root and could copy the mounted material into a layer, so pair credential fragments only with hook fragments you trust.

## Fragment structure

A fragment is a directory containing:

```
my-fragment/
├── Containerfile.fragment    # Builds the fragment OCI image
├── fragment.toml             # Metadata (name, version, description)
├── tree/                     # Files to copy into the base image
│   ├── etc/yum.repos.d/my.repo
│   └── etc/pki/rpm-gpg/RPM-GPG-KEY-my
├── mount/                    # Optional: build-time credential material, bind-mounted during the package and hook steps, never committed
└── hook/                     # Optional: build-time setup
    └── entrypoint            # The one file the tool runs
```

The `tree/` directory mirrors the target filesystem layout. Files are copied verbatim.

`name` in `fragment.toml` must be lowercase letters, digits, `.`, `-`, or `_` (1 to 64 characters, starting and ending with a letter or digit), because it becomes both a directory name and a Containerfile stage name. Names that don't match are rejected rather than rewritten. See [Fragment Format](docs/fragment-format.md#fragmenttoml-schema) for the full grammar.

If `hook/` contains any file, it must contain an executable file named `entrypoint`, and that is the only file osfragment-assemble runs, after package installation, with no arguments. Anything else under `hook/` is support material the entrypoint can reach at `/frag-hook/`, at any depth, and the tool never invokes it. A fragment with hooks and no executable `hook/entrypoint` fails to load. Fragment authors are responsible for setting the execute bit and for any required interpreters being available in the image at build time.

## Building your own fragments

Fragment images are standard OCI images. Each fragment directory contains a `Containerfile.fragment` that builds it:

```dockerfile
FROM scratch
COPY fragment.toml /fragment/
COPY tree/ /fragment/tree/
COPY hook/ /fragment/hook/
COPY mount/ /fragment/mount/
```

Each directory needs its own `COPY` with an explicit destination. A single
`COPY fragment.toml tree/ hook/ /fragment/` copies the *contents* of `tree/`
and `hook/` into `/fragment/`, leaving no `/fragment/tree/` or
`/fragment/hook/` for the tool to read. The `COPY mount/ /fragment/mount/` line is optional: include it only for fragments that carry build-time credential material.

Build and push to a registry:

```bash
cd my-fragment
podman build -f Containerfile.fragment -t quay.io/your-username/my-fragment:1.0 .
podman push quay.io/your-username/my-fragment:1.0
```

Then reference it in your manifest:

```yaml
fragments:
  - image: quay.io/your-username/my-fragment:1.0
    packages: [my-package]
```

See `examples/fragments/` for ready-to-use examples.

## CLI

### Generate a Containerfile

```bash
osfragment-assemble [OPTIONS]
```

- `--manifest <path>`: Path to manifest file (default: `osfragment-assemble.yaml`)
- `--output <path>`: Output Containerfile path (default: `Containerfile`)
- `--pin-digests`: Resolve and pin all image refs to sha256 digests
- `--self-contained <dir>`: Materialize fragment tree/hook payload into `<dir>`, alongside the generated `<dir>/Containerfile`, and package `<dir>` as a sibling `<dir>.tar.gz`. `<dir>` carries a `.osfragment-assemble` sentinel marking it safe to regenerate. The emitted Containerfile references no registry image except the base. Mutually exclusive with `--ocp` and `--output`. Fragment images are always pulled by digest internally in this mode regardless of `--pin-digests`, but that digest never appears in the output; `--pin-digests` still only controls whether the base image's `FROM` line is pinned.
- `--materialize-mounts`: With `--self-contained`, write fragment `mount/` material into the build context. Requires `--self-contained`. Without it, a composition whose fragments derive mount points refuses to generate self-contained output, because the material would land durably on disk in the context and its tarball; an empty `mount/` derives nothing and does not trigger the refusal. With it, the mount subtrees are written owner-only (directories at 0700), the tarball preserves those modes, and a `.gitignore` covering `fragments/*/mount/` is written into the context: git does not record file modes, so a committed context would publish the material world-readable.
- `--ocp [<path>]`: Generate a MachineOSConfig YAML for OpenShift (default: `machineosbuild.yaml`)
- `--pool <name>`: MachineConfigPool name for `--ocp` output (default: `worker`)

### Inspect a fragment

```bash
osfragment-assemble inspect <image-or-directory>
```

Examine a fragment's metadata and contents. Accepts a local directory path or an OCI image reference.

### List fragments in a manifest

```bash
osfragment-assemble list --manifest <path>
```

List fragments in manifest order (the order they'll appear in the generated Containerfile).

## Base images

osfragment-assemble composes build inputs for bootc image builds. Every generated Containerfile applies systemd presets (`systemctl preset-all`) and validates the result (`bootc container lint`); on a base without bootc, the lint step fails the build. MachineOSConfig output (`--ocp`) is a bootc target too: it builds OpenShift node OS images through the Machine Config Operator.

**The base image is never probed to decide behavior.** Default-path generation needs no registry access for the base, so it works against a base that exists only in local storage, or with no network at all. `--pin-digests` resolves digests from the registry, the base's included.

## Example fragments

The `examples/fragments/` directory contains 10 ready-to-use fragments:

- **epel** - EPEL repository configuration
- **tailscale** - Tailscale VPN with systemd preset
- **grafana** - Grafana repository and GPG key
- **postgresql** - PostgreSQL 17 repository
- **hashicorp** - HashiCorp repository (Vault, Terraform, etc.)
- **cis-hardening** - CIS security hardening configurations
- **node-exporter** - Prometheus Node Exporter
- **nginx** - nginx web server
- **awscli-zip** - AWS CLI v2 from the vendor's zip, installed into `/usr` rather than `/usr/local`
- **nvidia-driver-run** - NVIDIA driver from the vendor's `.run` installer, compiled for the image's kernel

`nvidia-driver-run` is the demanding one: a vendor installer that wants a TTY,
a compiler that must not survive into the finished image, and a kernel module
built for a kernel and a machine that are not the build host's. [Its
README](examples/fragments/nvidia-driver-run/README.md) is the tour of how much
a single fragment can carry.
