# Changelog

All notable changes to this project will be documented in this file.

and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- **Build mounts (`mount/`)** - A fragment may carry a `mount/` directory whose subtree mirrors target paths, like `tree/` does. Its material is bind-mounted onto the batched package install step and never committed by the builder, so package acquisition can authenticate from any build host: entitlement certificates, mirror client certificates, CA bundles for a TLS-intercepting proxy. Detection is presence-based, with no `fragment.toml` section and no new fragment kind. One `--mount` flag is emitted per derived mount point, always inline and never as a named stage, and a manifest entry for a fragment carrying `mount/` must be pinned by digest: a movable tag on an artifact that injects trust material into the package step is an invisible substitution point. Colliding mount targets, and targets that would hide the repo files or GPG keys the generator writes ahead of the install, fail generation. `inspect` renders the derived targets for a local fragment directory and for a registry image, and `list` reports them without pulling layers when the fragment carries the new `com.github.marrusl.osfragment.mounts` annotation, falling back to a full pull when it does not.

- **`--materialize-mounts`** - With `--self-contained`, writes fragment `mount/` material into the build context. Without it, a composition carrying `mount/` refuses to generate self-contained output, because that output carries no registry references and the material would have to land durably on disk in the context and its tarball. With it, the mount subtrees are written owner-only, the tarball preserves those modes, and a `.gitignore` covering `fragments/*/mount/` is written into the context: git does not record file modes, so a committed context would publish the material world-readable, and omitting it makes the build fail at the mount source instead.

- **`awscli-zip` example fragment** - Installs AWS CLI v2 from the vendor's self-contained zip into `/usr/lib/aws-cli` with symlinks in `/usr/bin`, instead of the `/usr/local` the installer defaults to. The first example with `hooks/` and no `tree/`: a script and a vendor blob, nothing else. Its point is the two arguments passed to `./aws/install` — `/usr/local` is the one path bootc has a documented opinion about, and left to itself the installer puts 259 MB of vendor payload there, which is either image-owned content squatting the administrator's path or, on a base using the ostree `/var/usrlocal` symlink, an install that is never updated after first boot. The ~70 MB zip is bind-mounted for one `RUN` and contributes zero bytes to the built image; `unzip` is installed and removed inside that same `RUN`, and only when the base does not already provide it. `fetch-awscli-zip.sh` downloads against recorded sha256 digests for both published architectures, and the zip is listed in `.gitignore`. Accompanied by `examples/manifests/awscli-zip.yaml`.

- **`nvidia-driver-run` example fragment** - Installs the NVIDIA driver from the vendor's `.run` self-extracting installer, compiling the kernel modules for the kernel of the image being built rather than the build host's. The first example whose `hooks/entrypoint` does real work, the first to carry a large binary payload as hook material, and the first to use `conflicts.fragments`. The ~350 MB installer is bind-mounted for one `RUN` and contributes zero bytes to the built image; the build toolchain is installed and removed inside that same `RUN` rather than declared as `packages.required`, so it leaves nothing recoverable in an earlier layer. The installer is never committed: `fetch-run-installer.sh` downloads it against a recorded sha256 and extracts the NVIDIA `LICENSE` that ships with it, and the blob is listed in `.gitignore`. Accompanied by `examples/manifests/nvidia-driver-run.yaml`.

- **`examples/manifests/demo.yaml`** - A combined manifest composing one fragment of each shape the format supports onto an unpinned `centos-bootc:stream10`: `epel` (repo-only, packages chosen by the consumer), `grafana` (repo, tree, and systemd preset), `awscli-zip` (hook-only, vendor zip), and `nvidia-driver-run` (hook plus tree, vendor `.run`). Both hostile-payload fragments land in the same image as the declarative ones.

- **`--self-contained <dir>`** - Materializes fragment tree/hooks payload into a local build context whose `Containerfile` sits alongside the payload, then packages the result as a sibling `.tar.gz`. The output directory carries a `.osfragment-assemble` sentinel file that marks it as tool-generated and safe to regenerate. The emitted Containerfile references no registry image except the base. Mutually exclusive with `--ocp` and `--output`.

### Removed

- **`baseType` manifest field and non-bootc base support** - osfragment-assemble composes build inputs for bootc image builds, MachineOSConfig output included, and the manifest no longer carries a field claiming otherwise. `baseType: container` used to drop the systemd preset and lint steps from the output; both steps are now emitted unconditionally, and on a base without bootc the lint step fails the build. A manifest declaring `baseType` with any value now fails the parse as an unknown field instead of being silently ignored.

- **Base image `containers.bootc` label probe** - `classify_base` is gone: generation no longer runs `skopeo inspect` against the base, and no classification step replaces it. Every base is treated as bootc, and the emitted `RUN bootc container lint` step verifies that at build time. The probe could not change the answer anyway: a present label, an absent label, and a failed lookup all classified as `bootc`. On the default path, a base that exists only in local storage now assembles with no registry contact and no stderr warning; `--pin-digests` still resolves the base's digest from the registry.

- **`phase` in `fragment.toml`** - The field and its `com.github.marrusl.osfragment.phase` annotation are gone, along with the `repos`-phase content restriction that forbade hooks and non-repo tree paths. It never decided placement: where a file lands has always been determined by its path, so a `config` fragment's repo definitions were hoisted ahead of the package install just like a `repos` fragment's. What it did do was sort fragments by phase weight before emission, which silently overrode manifest order and could decide which fragment won a path collision. Emission is now pure manifest order, matching the documented contract that manifest order is user intent. Stale `phase` keys are ignored rather than rejected, in the TOML and in the annotations, so previously published fragments keep resolving without a rebuild; rebuild them to drop the dead key.

### Changed

- **Unknown manifest keys now fail the parse** - A misspelled or removed key (`baseType` included) was silently ignored, so a manifest could carry a field that did nothing. The parser now rejects unknown keys with an error naming the field, at the top level and inside fragment entries alike, so a typo like `mirrorr:` fails the parse instead of doing nothing. This matches the rejection `[fragment.packages]` already applied.

- **`Classifying base image...` is no longer printed** - The line dates from when generation probed the base's `containers.bootc` label over the network. With that probe gone, classification is declared-or-default and the line narrated a no-op while implying a check the tool does not perform; the real verification is the emitted `RUN bootc container lint` step, which fails at build time on a non-bootc base. The default path is now silent.
- **Repo deduplication** - The tool no longer prints `skipping duplicate repo files from '<name>'`. It never skipped anything: every provider emitted its own COPY and the last one won. Fragments providing the same repo ID with identical content now pass silently, and the collision is reported where it always was, in the generated Containerfile's header comment. Conflicting content for the same repo ID still fails the build.
- **Namespace** - Manifest `apiVersion` is now `osfragment/v1alpha1` (was `bootc.io/v1alpha1`) and OCI annotation keys are now `com.github.marrusl.osfragment.<key>` (was `io.bootc.fragment.<key>`), moving both to a namespace this project controls. No compatibility path is provided: the old annotation keys are not read, so previously published fragments must be rebuilt and republished with the new keys or they fall back to layer extraction for metadata. Update `apiVersion` in existing manifests; the tool does not validate its value, so stale manifests parse without complaint.
- **Hooks entrypoint (breaking)** - If a fragment's `hooks/` contains any file, it must contain an executable regular file named `entrypoint`, and that file is the only thing the tool runs. Everything else under `hooks/`, at any depth, is support material the entrypoint can reach at `/frag-hooks/` but the tool never invokes. Alphabetical chaining of every file in `hooks/` is gone, with no fallback to discovery: a fragment carrying hooks and no executable `hooks/entrypoint` now fails to load, at assembly and at `inspect` alike. Unlike the `phase` removal, which retired a key the tool stopped reading, this changes what the tool runs — **every published fragment carrying hooks must be rebuilt**, or it stops loading entirely. Migration is usually a rename: `git mv hooks/configure.sh hooks/entrypoint`. Fragments needing several steps get an entrypoint that invokes the others, in whatever order and with whatever arguments they actually need.
- **Hooks** - Renamed fragment directory from `scripts/` to `hooks/`; the tool infers nothing from a hook file's extension, allowing Python, Perl, or any interpreter-based hook

- **Hook mount no longer carries `bind-propagation=rshared`** - Emitted hook mounts are now `RUN --mount=type=bind,from=<ref>,source=/fragment/hooks,target=/frag-hooks,z` in every mode, standalone and `--ocp` alike; `,z` is unchanged and `--self-contained` never carried the flag. Mount propagation governs only how sub-mount events cross a mount point, and nothing is ever mounted underneath `hooks/` — the tool bind-mounts the directory for one `RUN` and the entrypoint is a plain program — so the flag never had an effect to have. It was emitted as conservatism about matching MCO's validated mount options, which cost every reader of the generated Containerfile an unexplained flag in the line they study most closely. **This changes emitted output, so it invalidates the build cache for hook layers**; the first build after upgrading re-runs every hook.

### Fixed

- **Digest pinning no longer doubles an existing digest** - A manifest entry already written as `registry/repo@sha256:...` produced `registry/repo@sha256:...@sha256:...` in the emitted `FROM` lines under `--pin-digests` and `--self-contained`. Build mounts require the manifest to pin, so this stops being reachable only by manifests that pinned voluntarily.

- **Fragment names are validated before they reach a filesystem path** - A fragment's `name` becomes a directory name in the `--self-contained` build context and a stage name in the generated Containerfile, and was used as-is. A name containing `..`, a path separator, or a leading `/` escaped the intended directory: `../../escape` materialized into a sibling of the output directory entirely. Names must now match `[a-z0-9]([a-z0-9._-]*[a-z0-9])?`, at most 64 characters, checked once when `fragment.toml` is parsed. **This rejects fragments that previously loaded**: a name with uppercase letters, a leading or trailing separator, or any character outside the set now fails at load with a message naming the value. Names are rejected rather than rewritten, so a build always matches what the fragment author wrote. All example fragments already conform.

- **Hooks are detected whatever path form the layer uses** - Layer members were matched against the literal prefix `fragment/`, but a tar archive can legitimately carry the same file as `fragment/hooks/entrypoint`, `./fragment/hooks/entrypoint`, or `/fragment/hooks/entrypoint` depending on the builder that produced it. Only the first matched. A fragment whose hooks arrived in either other form had them dropped from detection while the files still landed in the built image, which silently skipped the `hooks/entrypoint` contract: a fragment with a non-executable entrypoint, or none at all, loaded clean. The same blind spot hid `fragment.toml` in a `/`-prefixed layer behind a "not found" error and made `--self-contained` materialize nothing at all. Layer paths are now normalized to one canonical relative form before any matching, so all three forms behave identically. **Fragments that previously loaded with their hooks ignored will now be checked against the entrypoint contract** and may fail until they carry an executable `hooks/entrypoint`.

- **Layer entry names that are not valid UTF-8 are rejected rather than materialized mangled** - A tar member name is arbitrary bytes on Unix, and layer paths were converted to UTF-8 lossily before `--self-contained` derived a destination filename from them. A name carrying invalid bytes materialized with replacement characters in place of those bytes, and two entries differing only in invalid bytes collapsed onto a single destination, the last one silently overwriting the first. Both were silent. Such an entry now fails the load with a message naming it, the same way the loader already treats `..` and absolute paths, so what the fragment author wrote is what lands on disk or the build stops and says why. Only layers carrying non-UTF-8 member names are affected; the example fragments and anything built by a conventional image builder are not.

- **The package step now cleans up dnf's plugin residue** - The emitted `RUN dnf install` removed dnf's own caches and logs but left what dnf's plugins write: the subscription-manager plugin creates `/run/rhsm`, `/var/log/rhsm` and `/var/lib/rhsm` on any invocation, the selinux-policy scriptlets create `/run/selinux-policy`, and ldconfig leaves `/var/cache/ldconfig/aux-cache`. None exist in a stock bootc base, so every composed image shipped three `bootc container lint` warnings that belonged to the tool rather than to any fragment. **This changes emitted output**, so the first build after upgrading re-runs the package step and everything after it.

- **`grafana` example fragment: bundled plugins are restored, and the account is declared** - Grafana ships the elasticsearch and zipkin datasource plugins inside the package directory and the RPM's `%post` moves them into the data directory, working around [grafana/grafana#123110](https://github.com/grafana/grafana/issues/123110). The server never looks there — the bundled-plugins path is derived from the homepath, not from `default.paths.data`, so with the unit file's own arguments it reads `/usr/share/grafana/data/plugins-bundled` — which leaves that directory empty and makes grafana silently re-download both plugins from grafana.com on first start. The fragment's entrypoint undoes the move, so the plugins load from disk with no network, and 23 read-only files stop riding in `/var` where image mode freezes them at first boot. The fragment also declares the grafana account in `sysusers.d` and its state and log directories in `tmpfiles.d`, which the RPM creates imperatively in `%post` and declares nowhere.

- **`nvidia-driver-run` example fragment: rhsm and ldconfig residue** - Its cleanup covered dnf's own caches and logs but not what dnf's subscription-manager plugin recreates on every invocation, nor the ldconfig aux-cache. As the last dnf caller in a composed image, whatever it left is what shipped. It now removes the same set the `awscli-zip` hook already did.

- **`nvidia-driver-run` example fragment: base-image build deps stripped by cleanup** - The entrypoint installed its build toolchain and `kernel-devel` unconditionally and removed them unconditionally, so composing the fragment onto a base that deliberately ships any of them, gcc and make included, stripped those packages from the finished image. Each package is now checked with `rpm -q` before install, only what the fragment itself installed is tracked, and only that is removed; a `kernel-devel` already present in the base is reported and left alone. The same guard the `awscli-zip` hook already applies to `unzip`.

- **`# Manifest:` header and `list` now name the real manifest** - Both the generated Containerfile's header comment and the `Manifest:` line printed by `list` were hardcoded to `osfragment-assemble.yaml` regardless of what `--manifest` was passed, so any manifest not at the default path produced output that misreported its own provenance. `Manifest` now carries the path it was read from and both call sites report it.
